# Route notes

## terminal

**Terminal switch**

one place to change the default terminal: `terminal.name` (`ghostty`, `foot` or `alacritty`; default `ghostty`) derives `desktop`, `appId`, `launch`, `launchTmuxSwitcher` argv lists, `imageProtocol` and the `TERMINAL` env (plus `PI_FORCE_IMAGE_PROTOCOL` for terminals without a kitty protocol); Home Manager consumers (enable gates, `xdg-terminal-exec`, mimeapps terminal association, niri/sway keybinds and app_id window rules) read `osConfig.terminal`

## nvme

**NVMe drive tuning**

DRAM-less Patriot M.2 P300 512GB: `services.fstrim.interval` is `daily` (upstream default `weekly`), and `systemd.services.fstrim` sets `restartIfChanged = false` plus `Restart = "on-failure"` / `RestartSec = "5min"`, because a `nixos-rebuild switch` once SIGTERMed the unit mid-run and nothing retried it until the next weekly tick — 132.3 GiB went untrimmed, collapsing sustained writes to 32-55 MB/s (reads unaffected at 841 MB/s) until a manual `fstrim` restored 1.7 GB/s / 606 MB/s. Full measurements in `docs/nvme.md`. The ZFS pool needs none of this (`autotrim=on`, `docs/zfs-pool.md`)

## firewall

**Network firewall**

Imported by `modules/network/default.nix`. Also owns fail2ban globals: `bantime`/`bantime-increment` (exponential escalation, `overalljails = true` shares the ban count across every jail, capped `maxtime = "168h"`), `ignoreIP` (RFC1918 only — the `[DEFAULT]` section it renders into is inherited by every jail including `sshd`, so no address range wider than that belongs here), the `sshd` jail's `journalmatch`, and `banaction`/`banaction-allports`/`packageFirewall` (set to `nftables-multiport`/`nftables-allports`/`pkgs.nftables` since 2026-09-22, so fail2ban bans through its own `inet f2b-table` instead of `-I INPUT 1`-ing mailcow's `netfilter` container out of first place — `docs/fail2ban.md`). The module body sits behind `lib.mkIf config.network.enableFirewall` (`modules/network/firewall.nix:8`), and that option defaults to `false` (`modules/network/default.nix:22-25`) with only `server` opting in (`hosts/configuration-server.nix:42`): on every other host neither the rules nor fail2ban exist, so any `networking.firewall.allowed*Ports` declared on a host that does not enable the firewall has no effect

## omp

**Oh My Pi (omp) coding agent**

the single omp implementation for every host (`modules/base.nix` imports it; the Home Manager module is gone and the old `mySystem.omp.enable` gate no longer exists). The agent itself is installed through the upstream input's `programs.omp.enable` option with `package = pkgs.omp` — the system packages in this module are only omp's runtime tools; MCP servers (`chroma`, `context7`, `telegram`) in `~/.omp/agent/mcp.json`; user-level agent context (`RULES.md`, `rules/`, `AGENTS.md`); mnemopi memory scoping; Layout is one file per concern beside `default.nix`: `packages.nix` (runtime packages), `secrets.nix`, `index-repo.nix` (service wiring and `linger`), `install.nix` (tmpfiles rules and the `config.yml` activation) and `settings/` (the generated payloads). `secrets.nix` and `index-repo.nix` are modules; `packages.nix` and `install.nix` return plain values that `default.nix` assigns to `programs.omp`, `environment.systemPackages`, `systemd.tmpfiles.rules` and `system.activationScripts.ompConfig`, because NixOS merges list options in reversed module-closure order: defining either list one module level deeper puts omp's rules ahead of jcode's. MCP servers include `telegram` (server-only, because `modules/omp/secrets.nix` declares the session secret only on that host, so no agent-level entry reaches `pc`/`notebook`/`fx516`; the resident `omp-mcp-telegram` unit serves streamable HTTP on 127.0.0.1:8932 and holds the single Telegram client; source pinned to the `labi-le/telegram-mcp` fork at revision `f086f7a8276fa4dcf368fa7eea7d918e5cd5ed72` (upstream `chigwell/telegram-mcp` plus sticker-pack tools and group-message waits)), `chroma` (`uvx chroma-mcp` against the ChromaDB at `services.index-repo.{host,port,ssl}` — the one declaration of that endpoint, shared with the server bind in `modules/chromadb.nix`) and `context7` (http); `tools.xdev = true` and `tools.xdevDocs = "catalog"` keep MCP schemas on demand through `xd://`; the chroma entry pins its uv environment with `--with 'pydantic<2.14'` because `chroma-mcp` 0.2.6 requires exactly `mcp==1.6.0`, whose `mcp.server.fastmcp` imports `eval_type_backport` from `pydantic._internal._typing_extra`, and pydantic 2.14 removed that symbol — unpinned, `uvx` re-resolves on every start, picks 2.14 and the server dies before the handshake (`ImportError: cannot import name 'eval_type_backport'`), which omp surfaces only as `MCP server not connected: chroma`. 2.13.x is the last line that keeps the symbol, and it still ships cp314 wheels: pydantic 2.11.10 has none and fails to build from source on the ambient Python 3.14 (`pydantic-core` 2.33.2), so `pydantic<2.14` is the narrowest constraint that both resolves against `mcp==1.6.0` and installs without compiling; a second pin, `--with 'chromadb==<config.services.chromadb.package.version>'`, holds the client at the exact version nixpkgs ships as the server instead of whatever `uvx` re-resolves from PyPI — measured 2026-10-10, `uvx` resolved `chromadb` 1.5.9 against the served `python3.14-chromadb-1.5.9`, and without the pin the next chromadb release would skew client from server with no signal; copy the version from the server package, never as a literal, so a nixpkgs bump moves both together; payload files (`models.yml`, `mcp.json`, `lsp.json`, `keybindings.yml`, `AGENTS.md`, `RULES.md`, `rules/`, `extensions/`, vendored skills) live in `modules/omp/` beside `default.nix` and deploy as individual store paths via `systemd.tmpfiles.rules` `L+` symlinks into `~/.omp/agent/` (`~/.omp/agent` and its `skills/`, `rules/`, `extensions/` dirs are tmpfiles `d` entries, mode 0700, owner from the `user` module arg); `config.yml` is the exception — a writable regular file (mode 600) written by `system.activationScripts.ompConfig`, because omp rewrites it at runtime under a lock and a store symlink fails with EACCES; settings pinned there that differ from omp defaults include `spelling.autocomplete = "off"` (no inline word-completion hints in the editor), `composer.tokenRate = true`, `stt.{enabled,language = "ru",submitTrigger = "never"}`, `memory.backend = "mnemopi"`, `modelRoleStorage = "project"` and `compaction.methodOrder`; agent context: `RULES.md` (always-apply), `rules/commit-style.md` (TTSR, fires on `git commit`), `rules/code-comments.md` (TTSR, fires on comment blocks in edits), `rules/project-naming.md` (rulebook, read via `rule://`), `AGENTS.md` (session background); `extensions/` holds the gate extensions `comment-gate.ts` / `commit-gate.ts` plus the indexer's `repo-register.js` (see Code indexer wiring); a rule's bucket follows its frontmatter — `condition`/`astCondition` wins over `alwaysApply`, a `description` with neither lands in the rulebook; rules are plain-markdown store paths, so editing a rule needs no Nix string escaping; memory scoping is `mnemopi.scoping = "per-project"` — one isolated bank per project, no shared bank; project-scoped MCP servers stay in that project's own `.omp/mcp.json` (this repo's `nix-control` server — see Other Files), not in the agent-level one; `models.yml` declares three direct providers, two of them discovery-only: `byesu` uses `discovery.type = "proxy"`, `closerouter` `openai-models-list` and `llm-labile` `litellm` — the last wrapped in `lib.optionalAttrs (litellmSecret != null)` so a host that does not receive the master key (fx516) gets no provider that would answer 401, whereas the older `closerouter` entry, keyed from the same secret, still hands such a host the literal env name instead; rosters then come from the endpoints instead of hand-kept lists (measured 2026-10-11 with the deployed keys: byesu publishes 31 ids whose `supported_endpoint_types: ["anthropic","openai"]` puts every claude/gemini/kimi row on `/v1/messages`, and closerouter publishes 121 ids of which 91 are chat rows, `context_length` is honoured while `max_output_tokens` and `pricing` are ignored and generic discovery never carries prices at all — `omp models <provider> --json` reports `pricingStatus: unknown`); `tokenharbor` sat here as the only static row until 2026-10-11, when it was deleted outright (provider, `secrets/tokenharbor-env.age`, `TOKENHARBOR_API_KEY` wiring in both agents, and the `.omp/models-tokenharbor.yml` preset) because its `/v1/models` answers `403 region_blocked` from this host's egress and no inference had ever worked through it; `llm-labile` is the one discovery that brings real metadata, because the gateway exposes management routes: five groups arrive with prices (`pricingStatus: fixed`, gpt-6-luna 0.10/0.50 per million tokens) and an OpenAI-backed group is dispatched over `POST /v1/responses` (seen in the `docker-litellm` journal while `omp -p --model llm-labile/deepseek-v4.1-flash` answered), not through the provider-level `api: openai-completions`, which only covers rows the manager cannot classify; a roster refresh after an upstream change is `omp models refresh <provider>`, and no rebuild is involved because discovery writes nothing back to the store symlink — the same probe leaves closerouter unable to serve inference at all (`402 insufficient_balance`); `llm-labile` additionally pins `step-5-preview` to `openai-completions` through `modelOverrides`, because discovery would otherwise dispatch it over the Responses route and Zen refuses that protocol for the free id (`400 ModelProtocolUnsupported`, measured 2026-10-11 — a deployment-side `mode = "chat"` did not change the choice); MCP servers are resident user units, not per-launch stdio children: `omp-mcp-chroma` wraps the same pinned `uvx chroma-mcp` command with `mcp-proxy --transport streamablehttp` on 127.0.0.1:8931 and `omp-mcp-telegram` runs the Telegram server's native `MCP_TRANSPORT=http` on 127.0.0.1:8932, so both `mcp.json` entries are `type = "http"` and an omp launch spawns no MCP subprocesses (measured 2026-10-23: tool refresh chroma 0.75 s / telegram 1.27 s → 0.16 s each, ~310 MB less RSS per omp, no `uvx` git or PyPI resolution at launch); both units carry `Restart=always` on loopback only

## flake

**Oh My Pi input, module and package overlay**

Input `omp` is upstream `github:can1357/oh-my-pi` and is consumed only for its `nixosModules.default` (upstream `nix/nixos-module.nix`, which contributes nothing but a `programs.omp.{enable,package}` gate over `environment.systemPackages`); `modules/omp/packages.nix` enables it and pins `package = pkgs.omp`; `modules/omp/default.nix` assigns that to `programs.omp`. `pkgs.omp` deliberately does NOT come from that input: the overlay takes `inputs.llm-agents.packages.${system}.omp`, which is the same from-source derivation upstream ships but is substitutable from `cache.numtide.com`, whereas the input's own `packages.default` has no cache and would build bun plus Rust locally. The installed version therefore follows the locked `llm-agents` rev, not the `omp` rev; ask what upstream publishes with `nix eval --raw github:numtide/llm-agents.nix#packages.x86_64-linux.omp.name`.

## jcode

**Jcode coding agent**

the single jcode implementation for every host (`modules/base.nix` imports it; the Home Manager module and `programs.jcode.settings` are gone). `~/.jcode/config.toml` is a `systemd.tmpfiles.rules` `L+` symlink into the store, like every other declared file, so the store content is the only writer and runtime drift is impossible; `system.activationScripts.jcodeProviderEnv` writes just the provider env files (`byesu.env`, `closerouter.env`, `pool.env`, mode 0600) from the agenix secrets, because those are credentials and cannot be store paths. Consequence, measured on 2026-09-30 against a store-symlinked config: jcode's own config writes fail loudly (`Error: Read-only file system (os error 30)`, exit 1) instead of silently rewriting the file; a CLI `provider add`, a TUI setting save and `jcode setup-hotkey`'s per-repo bake cannot persist, so every setting belongs in this module. Startup stays clean: the two startup migrations (`idle_animation`, `swarm_spawn_mode`) already see the declared values and only write their `~/.jcode/migrations/` stamp files, which stay writable. Rationale for the symlink over the previous writable copy: jcode's `Config::save()` rewrites the whole struct, which mangled declared floats (`0.8` came back as `0.800000011920929`, `0.3` as `0.30000001192092896`) and materialised sections the module never declared (`[display.colors]` with a full 22-role palette, `[terminal]`), so the running config depended on which writer ran last. Payload files (`mcp.json`, `prompt-overlay.md`, `AGENTS.md`, 22 vendored skill dirs from four pins — obra/superpowers, databasus humanizer, labi-le/agent-skills, asolfre/plantuml-rendering-skill) live in `modules/jcode/` and deploy as `systemd.tmpfiles.rules` `L+` symlinks into `~/.jcode/` and `~/AGENTS.md` (`~/.jcode`, `~/.jcode/skills` and `~/.config/jcode` are `d` entries, mode 0700, owner from the `user` module arg); runtime state (`sessions/`, `logs/`, `prompt-history.jsonl`, `migrations/`, sqlite files) is jcode's own and stays unwritable-by-Nix; `~/.jcode/no_telemetry` is a tmpfiles `f` marker, the config-level telemetry opt-out that `jcode telemetry disable` also writes (the `JCODE_NO_TELEMETRY` session variable was removed: only login shells saw it, and the running daemon kept writing milestone files); the opt-out stops delivery, not just local state: the daemon log holds 16 `telemetry payload send failed` attempts before the marker on 2026-09-30 and none after it across 2.5 h of active sessions, because session telemetry state only comes from the gated `begin_session_with_mode` and `record_turn` cannot emit without it (its `get_or_create_id` call can still leave a `telemetry_id` file on a fresh opted-out home, which sends nothing); the embedder is not part of the memory path — recall runs on Jev decisions and semantic compaction was its last consumer, so the model pin, the `embeddings` Cargo feature and `agents.memory_embedding_backend` are gone and `[compaction] mode` is `proactive` (an older `~/.jcode/models/all-MiniLM-L6-v2` symlink survives in `$HOME` from the deleted rule until removed by hand); a nix rebuild moves the client but not a running daemon: `jcode server reload` resolves its target from the self-update channel in `~/.jcode/builds`, which is empty here, so it reports "already running the newest binary" and the shared daemon keeps its old build until it is stopped (its next client launch then spawns the new one); Layout is one file per concern: `providers.nix` (the three provider profiles, the gateway pool derived from the litellm catalog, and the default route), `config.nix` (the rest of the generated `config.toml`, including the provider retry budget: `max_retries`/`retry_backoff_cap_secs` = 126/60, sized for two hours of retrying; only the OpenRouter/`openai-compatible` stream loop reads those two keys — it counts `max_retries` as attempts including the first and waits `min(1s·2^(k-1)·jitter, cap)` before attempt *k*, so 126/60 gives 1+2+4+8+16+32+60·119 ≈ 2 h 0 m against the 91 s of the old 8/30, while the OpenAI-native, Anthropic and Copilot loops keep their hardcoded `MAX_RETRIES = 3` and ignore both keys), `mcp.nix`, `hooks.nix` (gate wrappers + `repo-register.sh`), `skills.nix` (the vendored skill pins and their links), `provider-env.nix` (the credential files and the activation writer) and `default.nix` (NixOS side: options, tmpfiles, activation), so a new provider, skill or MCP server is one file beside `default.nix`. MCP servers in `~/.jcode/mcp.json` are exactly `chroma` (stdio `uvx chroma-mcp` against the ChromaDB at `services.index-repo.{host,port,ssl}`, carrying the same two `--with` pins (`pydantic<2.14`, `chromadb==<served version>`) as the omp entry — see that row) and `context7` bridged through `pkgs.mcp-proxy` with `--transport streamablehttp`, because jcode is stdio-only and logs-and-skips http/sse entries; `~/AGENTS.md` and `~/.jcode/prompt-overlay.md` are the only global instruction files jcode reads, and it never walks parent dirs; `[hooks] pre_tool` runs three independent scripts, each ignoring tools it does not own: `commit-gate.py` (commit-message shape, bash only), `comment-gate.py` (comment and example gate on write/edit, extension-scoped) and `git_upstream_gate.py` (blocks a push whose resolved destination is a different branch); all read the tool payload as stdin JSON and exit 2 to block; `[hooks] session_start`/`turn_start` run `repo-register.sh` with the hook pid (register only — no unregister, so the indexer's dead-pid scan reaps); `[providers.byesu]`/`[providers.closerouter]`/`[providers.llm-labile]` set `api_key_env` + `env_file`, and the keys are written 0600 to `~/.config/jcode/byesu.env`, `~/.config/jcode/closerouter.env` and `~/.config/jcode/pool.env` from `/run/agenix/byesu-env` and `/run/agenix/opencode-litellm-master-key` (which holds both `LITELLM_CLOSEROUTER` and `LITELLM_MASTER_KEY`), so no credential reaches the store; a custom profile is reachable non-interactively only through `--provider-profile <name>` (`-p` rejects anything outside its built-in value list), so `byesu` is used as `jcode run --provider-profile byesu -m claude-haiku-5-5`, and `byesu` still pins eight models by hand (three claude 5-5, four gemini, `kimi-k3`) with the models.dev context windows, because a jcode `openai-compatible` profile takes its roster from the live catalog but its capability metadata from nowhere else — the eight entries are metadata overlays over a 30-id live roster, measured 2026-10-11 in `docs/litellm.md`, not a list to keep in sync — the omp provider for the same endpoint dropped its list entirely for `discovery.type = "proxy"` on 2026-10-11 because omp merges a bundled catalog underneath; `llm-labile/deepseek-v4.1-flash` is this repo's own litellm gateway at `https://llm.labile.cc/v1` (nginx → `127.0.0.1:27015`), authenticated with the gateway master key: `writeProviderEnv` writes the file as `<variable>=<value>`, so the provider's `api_key_env` must be the *secret's* variable name (`LITELLM_MASTER_KEY`), not a fresh alias — an alias would leave jcode with an unset variable and an unauthenticated 401; the pool is also jcode's default route on every host that receives that secret (`default_provider = "llm-labile"`, `default_model = "deepseek-v4.1-flash"`, chosen from the secret's presence, not a host list), so interactive turns shuffle across the four accounts instead of draining one direct key, while fx516, no recipient of `opencode-litellm-master-key`, keeps the direct `opencode-go` profile and its `deepseek-v4.1-flash`; pasting an image needs jcode's own Ctrl+V (Alt+V works too), because foot's Ctrl+Shift+V and primary-paste carry text only: foot's `mime_type_map` has no image MIME, so an image-only clipboard makes the terminal emit an empty bracketed paste, which `handle_paste` drops with `Text paste: 0 chars, 0 lines` and no status notice (measured 2026-10-01 on six failed attempts, `wl-paste --list-types` showing `image/png`), while the Ctrl+V path falls through the empty text into `clipboard_image`/`wl-paste` and attaches `[image N]`; the delegation policy is instruction text in `~/AGENTS.md` (jcode has no stop gate and `turn_end` cannot block, so the mechanical half stays with jcode's auto-poke); project-scoped `.jcode/mcp.json` (`nix-control` + `nixos`, see Other Files) stays per-project and is not generated here; gate and register behavior is verified from the repo with `make gate-matrix` (`modules/jcode/gate-matrix.py`, fixtures in /tmp); the package is `inputs.llm-agents.packages.${system}.jcode` (`overlays.nix`), whose release build substitutes from `cache.numtide.com`, so no local Cargo feature override is applied

## deepseek-web

**Local FreeDeepseekAPI profile for jcode (DeepSeek-V4.1-Flash web proxy: provider `deepseek-web`, four composer-switch model ids, image input**

fresh proxy chat per jcode session on a shared proxy agent); Plug-in module imported by `modules/jcode/default.nix`; it contributes through the `jcode.extensions.{providers,hooks}` options that `default.nix` merges into the generated `~/.jcode/config.toml`. The `session_start`/`turn_start` hook keeps one constant proxy agent key (`jcode`) in `~/.config/jcode/deepseek-web.env` (the profile `env_file`) and starts a fresh proxy chat whenever the owning jcode session id in `~/.config/jcode/deepseek-session.state` changes, by posting the proxy's own `/new` command to `POST /v1/chat/completions` with `session=<key>`. It cannot use `POST /reset-session?agent=<key>`, which drops only the remote DeepSeek chat and deliberately keeps the proxy's local recovery history; the proxy then replays that history into the next fresh chat, and the new conversation answers with the previous chat's content. `/new` clears remote chat and history, so a new jcode chat starts empty while `/resume` keeps the chat of the session it restores. The key must stay constant: the provider resolves `extra_body` once when the server builds it, so a session-derived key would be frozen for the life of the server and every later chat would reuse it. The FreeDeepseekAPI proxy itself is not managed by this repo.

## space-bunny

**OpenCode Go `space-bunny-free` capability override for jcode (provider `opencode-go-bunny`: 1M context, text+image input, reasoning effort `high` by default)**

Plug-in module imported by `modules/jcode/default.nix` through `jcode.extensions.providers`. The base URL is the Zen tier `https://opencode.ai/zen/v1`, not the Go tier, and that changed on 2026-10-08: the Go tier dropped `space-bunny-free` from `/models` (it publishes `space-bunny` instead) and answers every chat request for the free id with HTTP 400 `Upstream request failed: Model is unavailable.`, while Zen still serves the id and one account key authenticates both tiers - so the free model stays reachable by moving the endpoint rather than by renaming the model. Zen also answers without `x-opencode-session` (measured the same day), which the Go tier rejects a request without. The provider's `/models` catalog publishes only `id/object/created/owned_by`, so jcode cannot see that the model reasons: without the declaration the picker shows `effort=none`, `provider.available_efforts()` is empty, and `/effort` is refused while the model still emits `reasoning_content` on its own. Values come from models.dev (`opencode-go/space-bunny-free`: context 1048576, input 524288, output 524288, `reasoning_options` effort low/medium/high/xhigh/max, modalities text, image, video). Two keys make effort usable on this endpoint. `supports_reasoning_effort = true` is the provider-level switch: it is what replaces the "Reasoning effort is not supported by the current model/profile" refusal, and that message names this exact key as its escape hatch, so without it the model silently runs at the endpoint's own default. `reasoning_effort` on the model entry sets the level jcode puts on the wire, and it must be a plain level: measured against the live endpoint, `none` is refused with HTTP 400 `invalid_request_error`, which is why the declared default is `high`. `swarm` and `swarm-deep` are jcode's own orchestration rungs, never wire values - `/effort swarm-deep` shows `Swarm Deep (Max + task graph) [Beta]` in the status bar and jcode sends `[agents] swarm_root_effort` / `swarm_deep_root_effort` (both default `max`) as the actual `reasoning_effort`, so nothing named `swarm*` ever reaches the endpoint and the 400 above says nothing about those rungs. Verified on this profile in a real TUI (2026-10-08): `/effort swarm-deep` is accepted, and a requested two-worker fan-out ran to completion with root and both workers on `space-bunny-free` at `zen/v1` (`API stream attempt 1/8 ... endpoint: https://opencode.ai/zen/v1`, five streams in that turn). The interactive picker stays absent and no config shape fixes it: bare `/effort` and the Alt+arrow stepper print "Reasoning effort not available for this provider." because that path is gated on `provider.available_efforts()`, and jcode 0.92.0 implements that trait method for OpenAI, Anthropic, OpenRouter, Gemini, Bedrock, Copilot, Cursor, Antigravity and Grok Build only - there is no openai-compatible implementation, so every custom profile gets an empty list whatever it declares (`model_catalog`, `allow_provider_pinning` and, measured in an isolated `JCODE_HOME` on 2026-10-08, `type = "open-router"` - the only enum value that routes to the OpenRouter runtime, which does answer this endpoint correctly - were all tried and none adds a rung). `/effort <level>` is therefore the only entry, and it works for every plain level plus both swarm rungs. The profile is a named profile instead of a `[providers.opencode-go]` block because a config profile that reuses a built-in profile id is only honored when its `base_url` differs from the built-in one (`is_user_named_profile`); the name is what surfaces in `/model` as `OpenCode Go` -> `space-bunny-free`. The `Failed to restore session reasoning effort 'swarm'` lines in the daemon log are the built-in `opencode-go` profile restoring an old session, not this one.

## maki

**Maki coding agent (pc, server, notebook)**

Package is `inputs.llm-agents.packages.${system}.maki` exposed through `overlays.nix` as `pkgs.maki`; it ships from the same `llm-agents` input as omp and jcode and substitutes from `cache.numtide.com`, so no Rust build runs locally. Layout is one file per concern beside `default.nix`: `mcp.nix` (generated `mcp.toml`), `skills.nix` (skill links), `lua/` (provider plugins), `skills/` (local `SKILL.md` payloads) and `AGENTS.md` (global instructions); `default.nix` assigns the tmpfiles `L+` symlinks. ## niri

## settings

**Common settings (nix settings, allowed packages), imported by every host through `commonModules`. `pc`/`server`/`notebook` also carry the GitHub API credential that keeps**

`github:` flake inputs resolvable: `secrets/nix-access-tokens.age` (recipients `all`) decrypts to `/run/agenix/nix-access-tokens` (owner `labile`, `users`, mode 0400) and reaches nix.conf through `nix.extraOptions = "!include …"` — a nix.conf fragment holding `access-tokens = github.com=<token>`, the same token nix sends to `api.github.com`. Why it exists: every `github:<owner>/<repo>` input is resolved through `api.github.com/repos/…/commits/HEAD`, the anonymous budget is 60 requests/hour per **egress IP**, and this host's GitHub traffic leaves through a shared Cloudflare address (`104.28.196.105` in the 403 body, while `api.ipify.org` reports the ISP address), so that budget is effectively always spent. Cost, measured 2026-10-12: `nix flake update llm-agents` printed `HTTP error 403 … API rate limit exceeded … using cached version`, exited 0, and **downgraded** the lock from `fdd62d5` (2026-10-10, omp 18.8.9) to `4bb57cf` (2026-10-09) — the stale rev is the only trace of the fallback. A/B measured after the fix: `nix --option access-tokens "" flake metadata --refresh github:nix-community/nixd` reproduces the same 403, the configured token resolves and unpacks the tree. It deliberately does not use `nix.settings.access-tokens`: `/etc/nix/nix.conf` is a store path (`/etc/static/nix/nix.conf` → `/nix/store/…-nix.conf`) and `modules/cache-push.nix` pushes build outputs to `cache.labile.cc`, so the token would be published there. `!include` rather than `include` because a missing or unreadable file is ignored: hosts outside `tokenHosts` (`fx516`) and a mangled mode degrade to unauthenticated nix instead of a failed activation, at the price of failing silently. The deployed value is this host's `gh` CLI OAuth token; rotate with `nix-control secret_write path=secrets/nix-access-tokens.age` (recipients unchanged, no rekey) plus `make switch`, or replace it with a dedicated read-only PAT to bound what a leak hands over

## index-repo

**Code indexer (`index-repo`)**

The indexer is an external flake (`index-repo.url` in `flake.nix`) that ships its own Nix modules. Its systemd user unit (`index-repo serve`) is defined by that module, so do not hand-write it. Connection options (ChromaDB host/port/ssl, debounce) are `services.index-repo.{host,port,ssl,debounce}`: `host`/`port` are the one declaration of the ChromaDB endpoint, because `modules/chromadb.nix` binds the server there and both agents' `chroma` MCP entries connect to it, so `192.168.1.2:8000` is written once. `users.users.<user>.linger = true` is required, because the server has no interactive login and therefore no user manager, so the user unit never starts without it.
